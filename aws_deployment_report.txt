VIVAHA - AWS DEPLOYMENT REPORT
Region: ap-south-1 (Mumbai)
Date: 2026-08-24

================================================================
1. SEARCH BUG (/search/profiles) - FULLY RESOLVED
================================================================

Three independent issues were stacked on top of each other, each one
masking the next until the previous was fixed.

--- Issue 1: Env vars silently wiped ---
Root cause: A failed Elastic Beanstalk config-deploy silently rolled
back the KAFKA_BROKERS and ES_ADDRESSES environment variables to an
earlier snapshot, leaving the API pointed at localhost:59200 and
localhost:59092 instead of the real supporting-services host.
Symptom: HTTP 500 internal_error
Fix: Re-applied both env vars together with the version-label redeploy
in a single `update-environment` call, to avoid re-triggering the same
rollback.

--- Issue 2: Missing security group rules ---
Root cause: Security group sg-058208ed4c5f06c64 never had ingress rules
opened for port 59200 (Elasticsearch) or port 59092 (Kafka). Redis
(56379) and MinIO (59000) had been opened earlier, but these two were
missed.
Symptom: HTTP 504 / complete request hang. Confirmed via SSM that a raw
curl from the Beanstalk EC2 instance itself to the ES host timed out
completely.
Fix: Opened both ports via aws ec2 authorize-security-group-ingress,
scoped to the VPC CIDR (172.31.0.0/16) only, not public.

--- Issue 3: Silent panic swallowing (found earlier in the session) ---
Root cause: sentry.Recover() (bare, no repanic) captured a startup
panic (CORS "conflict settings: all origins disabled") and reported it
to Sentry, but did not re-panic, so main() returned normally afterward
- exit code 0, zero log output, indistinguishable from a clean
shutdown.
Fix: main.go's deferred recover now re-panics after reporting to
Sentry, so real startup failures are visible in docker logs again.

Verification: GET /search/profiles?religion=Hindu&city=Mumbai now
returns HTTP 200 in ~59ms with the expected empty-result envelope.

================================================================
3. OUTSTANDING ISSUE (spotted, not yet fixed)
================================================================

nginx on the Beanstalk instance is rejecting POST /verification/id
uploads over ~1MB with "client intended to send too large body" -
seen repeatedly in production logs for 5-9MB ID verification photos
from real users. Root cause is nginx's default client_max_body_size
being too small. FIXED (2026-08-24, post-report): added
backend/.platform/nginx/conf.d/upload_size.conf setting
client_max_body_size to 15M, redeployed as application version
nginx-body-size-fix-v2. Verified nginx no longer rejects large
uploads.

================================================================
4. SECOND BUG FOUND WHILE VERIFYING #3 - IDENTITY VERIFICATION
   UPLOADS FAILING WITH "something went wrong" - FIXED
================================================================

After the nginx fix, a real upload to POST /verification/id still
failed, now with HTTP 500 "internal_error" ("something went wrong").

Root cause: cmd/api/main.go only calls s3Client.EnsureBucket() /
EnsureDocsBucket() when APP_ENV=dev - by design, since in staging/prod
the bucket is expected to be provisioned via infra tooling ahead of
time. Nobody had provisioned it for the fresh Mumbai MinIO instance:
the "matrimony-photos" bucket existed (created earlier, by hand or via
some initial dev-mode run), but the private "matrimony-verification-
docs" bucket used exclusively for ID-verification uploads was never
created at all. Every upload attempt failed inside
storage.DocumentUploader.UploadVerificationDoc with a bucket-not-found
error, surfaced to the client only as the generic internal_error
message.

Fix: created the missing bucket directly on the Mumbai MinIO instance
via `mc mb local/matrimony-verification-docs` + `mc anonymous set none`
(private, matching what EnsureDocsBucket would have done). This is an
infra/data fix, not a code change - the dev-mode gating in main.go is
intentional and was left as-is.

Verified: the same test upload that previously returned 500 now
returns HTTP 200 with success:true, a stored document, and a valid
presigned download URL.
